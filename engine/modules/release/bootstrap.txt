AUTOMATIC UPDATE ENTRYPOINT
release.updater owns consumer engine freshness and adoption. With web access, run its automatic update preflight at every runtime/session startup before ordinary account/domain work. Also run it before `reload LWAI`, before schema-sensitive migration/recovery where canonical compatibility matters, and before consequential work after the six-hour freshness TTL. A successful no-op check is silent. A successful update must preserve the user's original requested action across the engine swap, health-check the new engine, then continue that action under the new verified Production version.
Durable workspaces may persist only compact workspace-level engine metadata such as installed version, last successful check/update, last-known-good version, update policy and health. Session-only deployments keep equivalent metadata ephemerally. None of this metadata is account evidence or a routing key.

FIRST-RUN PERSISTENCE GATE
If and only if discovery confirms a genuinely new user with no existing LWAI state, resolve persistence before account identity onboarding:
1. Capability-detect supported storage actually exposed by the host.
2. If a verified writable provider is available, recommend creating an isolated private LWAI workspace and ask the user to choose `use cloud storage` or `continue session-only`.
3. If no verified writable provider is available, explain that session-only mode works but lacks durable cross-chat recovery and reliable persistent multi-account state. Invite the user to connect a supported provider in the host application (Google Drive is the most-tested option when available) and reply `storage connected`, or choose `continue session-only`.
4. Do not collect new account identity or create account_id/account storage before this choice is explicit.
5. After `storage connected`, capability-detect again. If cloud is chosen, create and verify an isolated LWAI workspace before identity intake. If session-only is chosen, acknowledge once and proceed without immediately repeating the prompt.
Existing users with a valid workspace skip this gate. Read-only providers are reference sources, not canonical persistence. Later `enable persistence` / `connect storage` may migrate supported session state without reset. A prior session-only choice may be re-offered later only through the benefit-triggered reminder rules in core.persistence/core.guidance.

MIGRATION
Follow releases/MIGRATIONS.json plus contracts/migration.md. Single-account migration generates immutable account_id, creates/registers Workspace Registry, registers existing database in place, sets active_account_id, preserves existing domain data and evidence metadata, then runs isolation/reload tests. Engine-only releases must not rewrite local account schema/state.

ARCHIVE / RESTORE
Starting over creates a new clean account and archives the previous registry entry by default. Archive is reversible; restore/unarchive preserves immutable account_id and history. Destructive deletion requires an explicit informed request.
