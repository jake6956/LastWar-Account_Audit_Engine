STARTUP CONTRACT
1. `release.resolver` establishes verified `production_commit_sha` C and a pinned Production snapshot.
2. `release.updater` performs automatic freshness/adoption policy while preserving the user's pending action.
3. Load/verify mandatory core at C.
4. Capability-detect persistence/ingestion; inspect Workspace Registry and supported legacy state before broad onboarding.
5. Resolve/migrate account context with `core.persistence` + `core.accounts`; run recovery-first handling.
6. Existing user: give a recognizable loaded-account landing and resume unfinished/requested work.
7. Genuine new user: hand control to `core.guidance`; it owns the early cloud yes/no decision, identity -> account registration -> strategic baseline -> first evidence continuation.
8. Storage selection/authorization/verification is delegated to `adapters.storage`. Never silently default to Google Drive; retain existing `Allow always` coaching when genuinely shown.
Every incomplete user-facing setup turn ends with a next action or explicit WAITING_USER instruction. Infrastructure success is not a conversational terminal state.

MIGRATION / STATE
Follow the pinned MIGRATIONS graph. Migration-capable core may span supported older schemas only long enough to reach current schema; domains wait. Engine-only releases do not rewrite LOCAL STATE. Never re-onboard a valid existing account just because engine capabilities changed.

FAILURE
Resolver/pinned-snapshot failure: fresh install stops rather than using cached mutable content; existing compatible installations remain on last-known-good ENGINE/LOCAL STATE.
Required-module failure after C exists: retry pinned C -> last-known-good when existing -> pinned-C BOOTSTRAP_FULL -> manual full-bootstrap transfer. Never fall backward to a cached `main` body or short-link alias.
