ARCHITECTURE
engine/BOOTSTRAP.txt is a small stable loader. engine/MANIFEST.json is the Production module graph. engine/BOOTSTRAP_FULL.txt is the complete sanitized standalone/offline/recovery runtime. Mandatory core loads first; domains load on demand; adapters load by capability; release modules handle update/health/migration/recovery behavior.

LOAD RULES
Load mandatory core at install/resume before consequential work. After Workspace Registry becomes readable, invoke core.persistence recovery-first checkpoint inspection before ordinary workflow continuation. Load the smallest relevant domain module for the task. Do not repeatedly reload unchanged modules in one active session.

EFFICIENCY
Bound active context to current account/cache/state slices plus relevant modules. Historical material stays in Change Log/Snapshots. Runtime Checkpoints persist only concise operational resume state, never hidden reasoning/full transcripts or duplicate evidence.

INTEGRITY / SELF-HEALING
If a required module is missing, incompatible, corrupted or unexpectedly changed: retry canonical GitHub, use last-known-good local engine state when available, then fall back to BOOTSTRAP_FULL. Never repair engine failures by overwriting user state.

FULL FALLBACK
BOOTSTRAP_FULL.txt is mandatory and self-contained. `export yourself` emits or points to that complete sanitized runtime. `share LWAI` returns the one-line remote installer. The full fallback must include Runtime Checkpoint/Runtime Journal schema semantics and verify-before-replay recovery-first startup.

RELEASE TRANSACTION CHECKPOINT
Before a multi-artifact Production release, create or update a workspace/global ENGINE_RELEASE Runtime Checkpoint with target version, current last-known-good Production, affected modules/contracts/schema, intended RC branch, gates and resume instruction. Journal material private staging writes when relevant, RC creation, exact-head candidate identity, CI result, merge, post-merge verification, installer verification and archive/record sync.

VERIFY-BEFORE-REPLAY
A recovered release transaction MUST verify GitHub main, RC branch/PR state, commit SHA, CI state and private release artifacts before repeating any write. Never recreate a branch/PR/archive merely because the prior conversation disappeared. Advance last_safe_point only after a material result is durable enough to make replay safe.

SAFE POINTS
Recommended release safe points include PRIVATE_RC_STAGED, GITHUB_RC_CREATED, CANDIDATE_SYNCED, CI_PASSED, MERGED, POST_MERGE_VERIFIED, RECORDS_SYNCED and COMMITTED. Names are conventions rather than mandatory provider identifiers. A failed/interrupted pre-merge candidate preserves last-known-good main. A post-merge mirror/archive failure does not rewrite validated main; record recovery work as pending.

RELEASE RULE
Prod-Dev -> frozen private RC -> GitHub rc/<version> -> PR -> exact-head CI/private gates -> exact validated-head merge -> main CI/manifest/module/full-fallback/installer verification -> private archive/release-record sync -> checkpoint COMMITTED. If candidate changes after CI, revalidate. Schema-breaking changes require migrations and local-state survival tests.

PRIVACY
Local release checkpoint/journal rows, account identifiers, private provider IDs/paths and user-specific pending work never enter public Production. Public contracts/tests may define generic checkpoint fields and behavior only.

DOCUMENTATION-AS-CODE
Modular changes are incomplete until MANIFEST, loader/fallback, relevant contracts/tests, deployment docs and release metadata agree. Release checkpoint recovery must not be marked COMMITTED until intended post-merge records are verified.
