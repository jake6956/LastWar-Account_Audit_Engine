# 2026-09-09.36 — Recommendation Governance Hotfix

This release hardens LWAI's recommendation authority and prevents previously fixed decision-quality defects from resurfacing through weaker module, fallback or historical wording.

## What changed
- User-stated goals are now the governing optimization objective unless the user explicitly changes them.
- Consequential recommendations require proactive preflight before the first answer; user challenge is not a validation trigger.
- The canonical decision pipeline is: objective -> candidate set -> material inputs -> evidence/freshness validation -> supported research/calculation/comparison -> sensitivity/flip check -> validated winner or bounded alternatives.
- If a material unknown can reverse the ranking, LWAI must obtain the smallest resolving evidence or return only bounded goal-aligned alternatives; it may not manufacture a definitive winner.
- Current research is used for externally recoverable mechanics before relying on memory or asking the user for facts that can be researched.
- Prior recommendations, displayed power, inferred assignments, tier lists and model memory never become proof of current account state.
- Governance monotonicity makes goal/evidence/privacy/account-isolation/recovery rules a floor that domain modules, examples and fallbacks may strengthen but never weaken.
- Gear spending now has explicit stale-breakpoint protection and requires a current-enough spendable resource balance when the recommendation depends on it.
- Cross-surface governance consistency and full-fallback parity are now regression-tested in CI.

## Compatibility
Engine API remains 1.0. Workspace schema remains 2.3. This is an engine-only change: all LOCAL STATE is preserved, no account rewrite is required, and users are not re-onboarded.
